[#MDCFG_PROGRAMMING_GUIDE]
=== Updating the MDCFG Table

This section is non-normative. It applies to an IOPMP that implements the MDCFG table (`HWCFG3.mdcfg_fmt` = 0; see <<#REG_EXT_HWCFG3, Hardware Configuration 3>>) and describes how software can change several `MDCFG(_m_).t` values at run time so that the MDCFG table is non-decreasing after every register write, that is, `MDCFG(_m_-1).t` {le} `MDCFG(_m_).t` for every _m_ with 0 < _m_ < `HWCFG0.md_num`. In a non-decreasing table, no two ranges overlap, so every IOPMP entry belongs to the MD selected by its own two bounds, and a change to `MDCFG(_m_).t` moves IOPMP entries only between MD _m_ and MD _m_+1. In any other table, the ranges of several MDs can contain the same IOPMP entry, which then belongs to the lowest-indexed of those MDs (see <<#MDCFG_TABLE, MDCFG Table>>), so an RRID associated with that MD is checked against IOPMP entries written for another MD. Software should avoid such a table rather than rely on this association.

Software writes the MDCFG registers in several accesses, so changing several values passes through intermediate tables, and whether each of them is non-decreasing depends on the write order.

For example, let `MDCFG(0).t` to `MDCFG(3).t` be {10, 20, 30, 45} and the target be {10, 40, 42, 45}. Writing `MDCFG(1).t` = 40 first produces the intermediate table {10, 40, 30, 45}, in which `MDCFG(2).t` < `MDCFG(1).t`; writing `MDCFG(2).t` = 42 first avoids it.

The order below assumes that the current table is non-decreasing. After reset, `MDCFG(_m_).t` can hold any value unless the implementation defines it, so the first programming of the table needs no particular order as long as it is completed while `HWCFG0.enable` is 0, when the IOPMP checks no transaction. If `HWCFG0.enable` is hardwired to 1, the IOPMP checks transactions from reset, so software should read the table first. If the reset values form a non-decreasing table, the order below applies; for example, from an all-zero table every value increases, so software writes from the highest index down to index 0. If some `MDCFG(_m_).t` in the current table is below `MDCFG(_m_-1).t`, whether from reset or from an erroneous write, no write order keeps every intermediate table non-decreasing, and software should treat every memory domain as affected during that update, as described in the notes at the end of this section.

==== Recommended Write Order

Let `mdcfg_t_current[m]` be the current value of `MDCFG(_m_).t` and `mdcfg_t_next[m]` be its target value, where both tables are non-decreasing. Software should write only the values that change, in the following order:

. every value that increases (`mdcfg_t_next[m]` > `mdcfg_t_current[m]`), from the highest index down to index 0; and
. then every value that decreases (`mdcfg_t_next[m]` < `mdcfg_t_current[m]`), from index 0 up to the highest index.

With this order, every intermediate table is non-decreasing. The two steps do not interfere with each other.

[NOTE]
====
The recommended order is only meaningful if the writes reach the IOPMP in program order. Unless the I/O region of the control port orders the writes, software should place a fence (for example `fence io,io`) between consecutive MDCFG writes. A fence orders only the accesses of one hart, and software may run on several harts, so it should also serialize the entire update, for example, with a lock or by performing all MDCFG updates on one hart.
====

==== Reference Implementation

In the function below, `WRITE_MDCFG_T(m, t)` writes the value `t` to `MDCFG(_m_).t`. The preconditions in the comment are the caller's responsibility.

[source,c]
----
/*
 * Rewrite the MDCFG table from mdcfg_t_current[] to mdcfg_t_next[] so
 * that the table is non-decreasing (t(m) >= t(m-1)) after every write.
 *
 * Preconditions (not checked here):
 *   - mdcfg_t_current[]: software's cached value of the table, matching the
 *     device and non-decreasing.
 *   - mdcfg_t_next[]: validated by software beforehand:
 *       mdcfg_t_next[m] >= mdcfg_t_next[m-1],
 *       mdcfg_t_next[m] == mdcfg_t_current[m] for m < MDCFGLCK.f,
 *       every mdcfg_t_next[m] is a value that MDCFG(m).t accepts
 *       unchanged (the field is WARL).
 *   - For every m with mdcfg_t_next[m] != mdcfg_t_current[m], no
 *     transaction is checked against MD m, or MD m+1 if it exists,
 *     during the update, for example, by stalling them via MDSTALL when
 *     the stall extension is implemented.
 *   - No other write to the MDCFG table reaches the control port until
 *     the update has been verified.
 *   - WRITE_MDCFG_T(m, t) reaches the device in program order.
 */
void update_mdcfg_properly(const uint16_t *mdcfg_t_current,
                           const uint16_t *mdcfg_t_next, int md_num)
{
    /* Increases, highest index first. */
    for (int i = md_num - 1; i >= 0; i--)
        if (mdcfg_t_next[i] > mdcfg_t_current[i])
            WRITE_MDCFG_T((uint16_t)i, mdcfg_t_next[i]);

    /* Decreases, lowest index first. */
    for (int i = 0; i < md_num; i++)
        if (mdcfg_t_next[i] < mdcfg_t_current[i])
            WRITE_MDCFG_T((uint16_t)i, mdcfg_t_next[i]);
}
----

Because `MDCFG(_m_).t` is WARL, software should write only values that the implementation accepts unchanged, as documented by the implementation or as determined by reading the table back, for example, during bring-up. If software verifies an update by reading the table back, it should complete the verification before it allows other writes to the MDCFG table and before it lets transactions be checked against the affected memory domains again, as described in the notes at the end of this section.

[NOTE]
====
The write order only keeps the table non-decreasing. An IOPMP entry that moves between memory domains keeps its contents, so a transaction checked against an intermediate table can be granted or denied by a rule written for another memory domain. Software should therefore update the table with the transferred IOPMP entries set to OFF or already programmed for their new memory domain, and keep transactions from being checked against the affected memory domains during the update, that is, MD _m_ and MD _m_+1 for every changed `MDCFG(_m_).t`, for example, by stalling them as described in <<Program_IOPMPs, Safe Runtime Configuration>> or by deassociating them from every RRID in the SRCMD table beforehand. If software reads the table back to verify the update, it should fence the reads after the final write and before the write that resumes the transactions.
====

[NOTE]
====
If software reprograms the address of a transferred IOPMP entry _i_ and IOPMP entry _i_+1 selects TOR, the region of IOPMP entry _i_+1 changes as well, so the affected memory domains also include the memory domain of IOPMP entry _i_+1.
====
